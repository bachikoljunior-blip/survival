## 0. この文書は何で、何ではないか

**である:**

- 現在有効なコンセプトに対して、各要素で何を目標品質とするかを、具体的な参考作品に紐づけて宣言したもの
- その目標を、この リポジトリで実行できる検証に変換した基準表
- 現在の CINDERLINE と目標との差分の、証拠付きの記録

**ではない:**

- **新しい完了条件ではない。** Gate A〜D の完了条件は `docs/DONE.md` のままであり、`docs/directive.md` §18 は「新しい基準を発明しない」と定める。本文書の各基準は、既存の directive 条項（§4/§6/§7/§8/§9/§10/§11/§12/§13）を観察可能量へ翻訳したもので、条項を追加しない。基準表の「閾値の出所」列がその対応を示す
- **参考作品の計測結果ではない。** 本実行環境で参考作品を起動・計測・撮影・並置比較したことは一度もない。参考作品側の記述は**一般化された設計原則**であり、計測値でも引用でもない
- **専門家承認・ブラインド評価・実機計測の記録ではない。** いずれも実施していない

### 誠実性の宣言（`docs/directive.md` §15 / §13）

| 主張しないこと | 現状 |
|---|---|
| 参考作品との並置比較を実施した | **していない。** 参考作品を実行した事実がない |
| 参考作品の数値（フレーム時間・ドローコール等）を計測した | **していない。** 本文書に参考作品側の数値は1つも無い |
| 専門家が本作を承認した | **していない** |
| ブラインド評価を実施した | **していない**（`PROJECT_OPERATING_PROTOCOL.md` §18 の source-blind tester は未実行） |
| 実機（iPhone SE 第3世代）で計測した | **していない。実機が存在しない**（`docs/STATE.md` B1） |

参考作品の「評価」「評判」に関する記述は、**一般に確立した受容の要約**であり、本セッションで実施した調査・集計・専門家確認ではない。この区別は基準表の判定には使わない — 判定に使うのは CINDERLINE 側の実測だけである。

## 2. 選定規則

### 2.1 選定軸（ユーザー指定）

各作品は5軸すべてで説明する。1軸でも説明できない作品は採用しない。

1. **対象要素の実際の品質** — 知名度・売上ではなく、その要素で何を解いているか
2. **専門家およびプレイヤーからの評価**
3. **長期的な評判** — 発売直後の熱ではなく、時間が経っても参照され続けているか
4. **現在のゲームとの適合性** — §1 のコンセプトが解こうとしている問題と同じ問題を解いているか
5. **対象端末や制作規模への応用可能性** — その品質がアセット予算に由来するなら、本プロジェクトでは再現できない。**再現できない基準を掲げることは、基準を持たないことと同じである**

### 2.2 作品数を増やさない規則

- 1つの作品が複数要素で最適なら、**共通して使う**。本文書では 10 作品で 19 要素を担当し、うち4作品が複数要素を担当する
- 新しい作品を足すのは、既存ロスターのどれもがその要素で明確に劣るときだけ
- 「有名だから」「他にもあるから」で足さない

### 2.3 模倣禁止（`docs/directive.md` §3）

参考作品から取るのは、**一般化できる設計原則・品質基準・完成度・問題解決の方法**だけである。

**取ってはならない:** キャラクター、物語、世界設定、地名、マップ、ミッション、台詞、UI の見た目、アイコン、演出、音楽、効果音、モデル、テクスチャ、特徴的意匠。

各作品の「**取らないもの**」を §4 に明示する。これは装飾ではなく、コンセプトの汚染を防ぐための境界線である。

**機械検査:** `node tools/check_benchmarks.mjs` が、出荷されるソース（`src/` `public/` `index.html` `styles.css`）に参考作品の固有名詞が混入していないことを検査する。検査語は §4 の一覧に対応する。

### 2.4 基準を弱めない規則（ユーザー指定）

**現在の実装を合格させるために閾値を下げてはならない。**

機械検査で担保する。各基準の `ID + 基準 + 閾値` の sha256 を `AI_DEVELOPMENT/BENCHMARKS/criteria.lock.json` に固定し、`tools/check_benchmarks.mjs` が変更を検出する。閾値を変えた場合、**§9 変更履歴にその基準 ID と理由を書かない限り検査が失敗する。**

## 4. 作品ごとの「取るもの／取らないもの」

### W1 — Dark Souls (FromSoftware, 2011) → 戦闘・移動・アニメーション

- **軸1（要素の品質）**: 攻撃の発生・持続・硬直、被弾の確定、スタミナの役割が、装備や数値ではなく**時間**で表現され、プレイヤーが負けた原因を必ず特定できる
- **軸2・3（評価・長期評判）**: 発売後10年以上、後続作品がこの入力契約を規範として参照し続けている類型
- **軸4（適合性）**: CINDERLINE の操作語彙は HIT / HEAVY / ROLL / GUARD ＋ ロックオン ＋ スタミナで同型。レンは戦闘者ではなく逃走が常に有効という設計も、走り抜けが正当解であるこの系譜と矛盾しない
- **軸5（応用可能性）**: この作品の戦闘品質は**アニメーションの忠実度ではなくタイミングと可読性**に由来する。低ポリゴン・実行時生成リグでも同じ基準を満たせる
- **取らないもの**: 難度設計、ボス中心の構造、篝火とエスト瓶の経済、レベルとステータス成長、断片的なロア提示の作法、世界設定、キャラクター、UI の見た目、**および狭所のロックオンカメラ**

### W2 — Dishonored 2 (Arkane Studios, 2016) → 世界設計・探索・AI・進行

- **軸1**: 密度の高い単一地区に、垂直経路・近道・代替ルート・能力による再訪を、ランドマークで自己位置を保てる形で詰めている
- **軸2・3**: レベルデザインの参照先として長く引かれ続けている
- **軸4**: `docs/directive.md` §7 が列挙する体感的な広さの作り方（垂直経路／視認できるランドマーク／入れる屋内／屋上／地下／近道／後に開放される封鎖路／代替ルート／見通し／再訪）と一致する。CINDERLINE も「広さを密度に交換」する設計
- **軸5**: 当該品質は**レベルの構造**に由来し、アセット予算に由来しない。手続き的モジュール建築でも同じ構造は作れる
- **取らないもの**: 超常能力そのもの、暗殺という行為、階級社会の世界観、混沌システムの数値、ステルス失敗の罰則設計、地名、キャラクター、UI

### W3 — Alien: Isolation (Creative Assembly, 2014) → UI（HUD）・音響・環境ハザード

- **軸1**: 見えない脅威を、**不完全な計器と音**だけで読ませる。計器は答えを教えず、読む行為そのものにコストと判断を要求する
- **軸2・3**: 音響設計と脅威の提示について、発売後に評価が上がり続けた類型
- **軸4**: CINDERLINE の空気メーターは同型の問題を解いている — ppm は目に見えず、メーターを読むのは**動詞**である（`src/ui/hud.js:78-84`）。音が位置情報として機能しなければ、ガスも敵も読めない
- **軸5**: 当該品質は情報設計と音の配線であり、アセット予算に依存しない。CINDERLINE の音は全て WebAudio 合成で、同じ配線を実装できる
- **取らないもの**: ホラーというジャンル、怪物、SF 設定、レトロフューチャーの意匠、モーショントラッカーの見た目・音・挙動、世界観、キャラクター

### W4 — Disco Elysium (ZA/UM, 2019) → 物語・キャラクター

- **軸1**: 悪役を置かずに、全員が自分の実務的な理由で対立する構造を、説明台詞なしに会話だけで成立させている。**声（語彙・構文・沈黙）で人物を書き分ける規律**
- **軸2・3**: 物語とキャラクター表現の参照先として定着している
- **軸4**: `docs/bible.md` 柱3「誰も金のために嘘をついていない」と同じ設計問題。クライチクが追い詰められた時にちょうど受動態と条項番号へ手を伸ばす、という書き分けは、この craft の適用である
- **軸5**: 小規模スタジオ制作であり、文章量ではなく**書き分けの規律**が品質を作っている。対話ノード224・6299語という本作の規模でも適用できる
- **取らないもの**: スキルが人格として喋る構造、超現実要素、政治思想の具体、世界設定、地名、キャラクター、口調、比喩、物語、UI の見た目

### W5 — Fallout: New Vegas (Obsidian Entertainment, 2010) → 選択と結果

- **軸1**: エンディングが最終メニューではなく**蓄積された世界状態**から決まり、エピローグが「誰がどうなったか」を個別の決定に結びつける
- **軸2・3**: 発売直後ではなく時間とともに評価が上がった典型で、知名度ではなく設計で参照されている
- **軸4**: `docs/directive.md` §6 は「それまでの全てを上書きする最終メニュー選択を避ける」と明示的に定める。CINDERLINE の可変エピローグ8ビートは同型の装置であり、**現在それが機能していない**（IMP-01）
- **軸5**: 当該品質は記帳（フラグ・前提条件・排他状態）の設計であり、制作規模ではなく規律の問題。`tools/validate.mjs` の双方向フラグ検査は既に同じ思想で書かれている
- **取らないもの**: 派閥、世界設定、レトロフューチャー、カルマと評判の数値表示、スキルチェックの提示形式、地名、キャラクター、台詞

### W6 — God of War (Santa Monica Studio, 2018) → カメラ

- **軸1**: 近距離の三人称カメラが、狭所でもカットに逃げずに可読性を保つ。衝突・遮蔽・追従・framing が一貫した規則で動く
- **軸2・3**: カメラワークそのものが評価対象として語られる数少ない作品
- **軸4**: CINDERLINE の空間は路地・屋内・屋上・9mの陥没孔であり、**狭所と高低差でカメラが壊れないこと**が成立条件。ロックオンも同じ問題を持つ
- **軸5**: カメラ品質はコードと調整値であり、アセット予算に由来しない。本作の `ThirdPersonCamera` に同じ規則を実装できる
- **取らないもの**: ワンカット演出という枠組み、肩越し戦闘の間合い設計、シネマティックな見せ場、神話の世界観、キャラクター、UI

### W7 — INSIDE (Playdead, 2016) → 映像

- **軸1**: 幾何の情報量ではなく、**光の階層・限定パレット・シルエット・霧による奥行き分離**で、成熟した緊張感のある画を作っている
- **軸2・3**: 制約下の art direction の実例として長く参照されている
- **軸4**: `docs/directive.md` §9 の指示「ジオメトリよりマテリアル」「ライティング階層の設計。**これが使える最大の武器である**」「シルエットと構図」の、ほぼそのままの実例
- **軸5**: 小規模スタジオ制作。ただし**適用限界がある** — この作品のポストエフェクト物量はモバイル WebGL の GPU 予算では成立しない。取るのは**構図と光の規律**であって、エフェクトの物量ではない
- **取らないもの**: 2.5D の構図、固定カメラ演出、ポストエフェクトの物量、色そのもの、世界観、主人公、演出、音

### W8 — The Last of Us Part II (Naughty Dog, 2020) → UI（メニュー・字幕・アクセシビリティ）

- **軸1**: アクセシビリティ設定を後付けのオプション群ではなく設計の一部として提示している。字幕の話者表示、UI 拡大、高コントラスト、動きの低減、ホールド／トグルの選択などが体系として揃う
- **軸2・3**: アクセシビリティの参照先として定着している
- **軸4**: `docs/directive.md` §11 が要求する項目と重なる。本作は既に設定を17項目実装しており、**残りの未実装項目（ホールド／トグル、色非依存の状態表現、チュートリアル）が明確な差分になっている**
- **軸5**: **これらの実装費用は低い。** モバイル制作規模で適用可能な数少ない AAA 由来の基準である
- **取らないもの**: **アニメーション・モデル・照明の忠実度**（本プロジェクトの制作規模では再現不能であり、基準に使えば嘘になる — §3 の不採用表を参照）、物語、キャラクター、UI の見た目、暴力表現

### W9 — Genshin Impact (miHoYo, 2020) → タッチ操作・性能

- **軸1**: iPhone を含むモバイル端末上で、3D 三人称アクションを**仮想スティック＋カメラドラッグ＋アクションボタン**で成立させている。端末階層に応じた解像度・LOD・影・エフェクト密度の調整を、同じコンテンツのまま行う
- **軸2・3**: タッチ操作の評価は割れるが、**この端末クラスでこのジャンルが成立するという実在証明**としての参照価値は高い。ここで取るのは操作の好悪ではなく、レイアウトと段階的劣化の設計
- **軸4**: CINDERLINE の操作モデル（左42%スティック／右58%カメラドラッグ／右タップでロックオン）は同じ制約を解いている。`docs/directive.md` §13 の「品質ティアと自動劣化」も同じ設計
- **軸5**: **適用限界を明記する** — ネイティブアプリであり WebGL ではない。本文書は両者の数値を比較しておらず、比較できない。取るのは**階層設計の考え方**だけである
- **取らないもの**: ガチャと収益設計、キャラクター切替、UI の見た目、アイコン、世界観、アート、演出、音楽

### W10 — Factorio (Wube Software, 2016) → 安定性

- **軸1**: 決定論的な固定ステップシミュレーション、セーブのバージョン移行、長時間セッションでの安定性、失敗時に何が起きたかをユーザーへ提示する設計を、長期にわたり維持している
- **軸2・3**: 工学的な信頼性そのものが評価対象として語られる稀な作品
- **軸4**: CINDERLINE は既に 60Hz 固定ステップ（`src/core/engine.js:13`）で動いており、**現在の最優先課題がセーブ移行（GB-H1）と起動後エラー回復（GB-H2）である**。同じ領域を最高水準で解いている作品を基準にする意味が大きい
- **軸5**: 小規模スタジオ制作。当該品質は規律であり予算ではない
- **取らないもの**: ジャンル、UI、世界観、モッディング機構、マルチプレイ、アート

## 5. 要素別の基準

### 表の読み方

- **閾値の出所**: `directive`（`docs/directive.md` の既定値をそのまま使う）/ `本プロジェクト`（本文書で設定した値。参考作品の実測値ではない）/ `参考原則`（数値ではなく満たすべき性質）
- **状態**: `適合` / `未達` / `部分` / `未計測` / `人間のみ`

## 8. コンセプト変更時の手順

ユーザーがコンセプトの一部を変更した場合:

1. `docs/directive.md` §1 と `docs/bible.md` を先に更新する（正本が先、本文書は後）
2. 本文書 §1 を更新し、`concept_revision` を上げる
3. 変更が影響する**要素だけ**を洗い出す。影響しない要素の参考作品と基準は**維持する**
4. 影響を受けた要素について、現在の参考作品がまだ最適かを §2.1 の5軸で再判定する
5. **不適合になった場合に限り**、より適切で**同等以上の品質**を持つ作品へ差し替える。作品数は増やさない（§2.2）
6. 差し替えた場合、新しい基準は旧基準と同等以上の厳しさでなければならない。§9 に旧基準・新基準・理由を記録する
7. `node tools/check_benchmarks.mjs --relock` で lock を更新し、§9 に該当 ID を書く

**禁止:** 現在の実装を合格させるための差し替え・閾値変更。`tools/check_benchmarks.mjs` が lock 差分を検出し、§9 に記録の無い変更を失敗させる。
