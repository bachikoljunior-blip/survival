## 0. 環境と前提

- リポジトリ: `bachikoljunior-blip/survival` / 作業ブランチ元: `main`
- レンダラ: Three.js（バージョンを1つに固定し、勝手に変えない）
- ビルド: Vite。`base: './'` を設定し、`.nojekyll` を置く（GitHub Pages サブディレクトリ対応）
- テスト: Vitest（ユニット・統合）+ Playwright（ブラウザスモーク）
- CI: PR で lint + test + build、`main` で Pages デプロイ
- ドキュメント・コミットメッセージ・ゲーム内テキストの言語: 日本語
- 追加ライブラリは MIT / Apache / CC0 互換のみ。採用理由を `docs/assets.md` に記録

**開発者は iPhone しか持っていない。** PC もローカル開発環境もない。全ての作業はリポジトリ内で完結させ、人間の手作業を前提にした手順を設計に組み込まないこと。

### 既存資産の起点利用

既にゲーム実装が存在する場合（リポジトリ内、または開発者が提示するもの）、**白紙から作り直さず、それを起点として利用してよい。** ただし以下を守ること:

- 起点にする場合も §5 の創作ディスカバリーは実施する。既存実装のタイトル・設定・システムを無条件に継承しない。§2 の非事前決定ルールは既存資産にも適用される
- 既存コードを §12 のアーキテクチャ要件と §13 の性能バジェットに照らして評価する。満たさない部分は改修するか破棄する。「既にあるから」は残す理由にならない
- 何を継承し、何を捨て、なぜそう判断したかを `docs/bible.md` に記録する
- 既存アセットは `docs/assets.md` でライセンスを確認できないものを使用しない
- 起点を活かすことでスコープを広げない。§4 の削る順序は変わらない

## 1. 固定ブリーフ

以下は変更不可。それ以外は全て制作過程で発見・設計・検証・正当化すること。

- ジャンル: 三人称オープンワールド アクションRPG、サバイバルの緊張感を伴う
- 舞台: 信憑性のある危機の後の、廃墟化・隔離・部分崩壊した現代都市
- トーン: 地に足のついた、成熟した、緊張感のある、人間的な。深刻だが陰惨一辺倒にしない
- アートディレクション: リアル志向（ピクセルアート・カートゥーン・パロディ不可）。ただし §9 の現実的制約に従う
- 物語: 強いキャラクター、劇的緊張、意味のある選択、伏線と回収を備えた完全オリジナル
- プラットフォーム: モバイルWebブラウザ（iOS Safari / Android Chrome）
- 基準端末: iPhone SE 第3世代、横向き
- デプロイ: 静的ビルド（GitHub Pages）
- 入力: タッチ優先。キーボード/マウスは開発用に維持

## 2. 非事前決定ルール

テンプレートを埋めるために内容を決め打ちしないこと。

以下を自動的に採用してはならない: 5幕構成 / 3つの派閥 / 4人の仲間 / 6つの地区 / 家族失踪もの / 企業の陰謀 / 生物災害。禁止ではないが、比較検討の結果として最強だと示された場合のみ選べる。

**実質的に異なる方向性を最低3案作り、書面のスコアカードで比較すること。** 評価軸: 独創性、テーマの深さ、ゲームプレイの可能性、感情的な賭け金、モバイル実現性、完遂可能なスコープ、意味のある帰結を生む能力。

キャラクター数・章数・地域数・クエスト数・システム数・分岐数・エンディング数は、各要素に与えられる深さと、高品質で完遂できる量から決定する。**少数の優れた要素を、多数の浅い要素より優先すること。これがこのドキュメントで最も重要な設計指示である。**

日常的な創作判断をユーザーに聞かないこと。証拠・テスト・比較で解決できない、真にブロッキングな判断のみ質問する。

## 4. スコープ管理

**広く空虚な世界より、小さく密度の高い完成した世界を作る。**

到達可能な全エリアは最低1つの意味ある機能を持つこと: 物語、戦闘、移動、発見、資源獲得、キャラクター描写、世界観、パズル、戦術的位置取り、近道、可視の帰結。

反復的な水増し、コピペ部屋、無意味な移動時間、汎用おつかい、無意味な収集物、チェックリスト設計、他作品にあるからという理由だけの機能を排除する。

品質基準に達しない機能は、その周りにコンテンツが広がる前に、再設計・簡略化・統合・削除する。機能一覧を保つためだけに弱い実装を残さない。

**削る順序**（上から先に削る）: 追加エンディング → 追加地区 → システム的機能（天候・クラフト・拠点） → 敵アーキタイプ数 → クエスト数 → エフェクト密度。

**絶対に削らないもの**: オープニングからエンディングまでの完走可能な導線、セーブ/ロードの整合性、タッチ操作性、フレーム安定性。

## 5. 創作ディスカバリー（Gate A まで）

作成者と批評者を分離した独立エージェントで実施する。各コンセプトは最低限これを定義すること: プレイヤーファンタジー / 中心的な劇的問い / 都市が現状に至った理由 / 分単位の行動 / 探索が重要な理由 / サバイバル圧の源 / アクションと物語の相互作用 / 独創性の所在 / モバイルWebで完遂できる範囲 / エンディング後に残る感情。

派生的、物語と機構が乖離、不可能なコンテンツ量に依存、完成不能、のいずれかに該当する案は棄却する。

方向性を決定したら `docs/bible.md`（プロダクションバイブル）を作成する。内容: 創作の柱と明示的なアンチ柱 / 前提とテーマ / プレイヤーの役割と動機 / 世界設定の歴史と規則 / ワールド構成と進行ロジック / コアループ / 戦闘と移動の哲学 / 進行と経済 / 物語構造 / キャラクター相関図 / クエストと帰結モデル / ビジュアル言語 / オーディオ言語 / モバイル操作モデル / 技術アーキテクチャ / アセットと性能バジェット / リスク登録簿 / 受け入れ基準。

**バイブルには以下のスコープ確定数値を必ず記載すること。Gate C の判定はこれを参照する:**
エリア数 / クエスト数 / エンディング数 / 敵アーキタイプ数 / 想定プレイ時間 / 対話ノード数の概算。

**この数値が、このプロジェクトが高品質で完遂できない量なら、今ここで削ること。** コンテンツ生産が始まってからでは手遅れになる。

独立した批評エージェントがバイブルを、ご都合主義・矛盾・動機の弱さ・派生性・過大スコープ・浅いシステム・ゲームプレイと物語の断絶・モバイル実現不可能性の観点から攻撃する。Gate A を通過するまで改訂する。

## 6. 物語要件

**物語はプレイ可能なビルドに実装されていること。詳細な物語ドキュメントだけでは要件を満たさない。**

- 具体的な人格・能力・限界・内的葛藤・続ける理由を持つ主人公
- 主人公を助けるためだけに存在しない、独自の生活と動機を持つ脇役
- 恣意的な悪ではなく、理解可能な目的に根ざした敵対的圧力
- プレイヤーの行動によって激化する中心的葛藤
- 公正に伏線が張られ、回収される謎
- 理解可能な賭け金を持ち、即時と遅延の両方の帰結を伴う選択
- 出来事とプレイヤーの振る舞いによって変化しうるキャラクターアーク
- 蓄積された決定と行動によって獲得されるエンディング

派閥を置くなら、内部対立・信じられる美徳・害のある欠陥・行動の実利的理由を持つこと。仲間を置くなら、独自目的・境界線・変化する意見・ゲームプレイ上の独自性・正当な理由があれば離反する能力を持つこと。**どちらも必須ではない。** 選んだ物語が必要とする場合のみ含める。

分岐は孤立した台詞以上を変えること: 信頼関係 / 得られる助力と敵対 / ミッション経路 / エリアと資源へのアクセス / 場所の状態 / 市民やコミュニティの帰結 / 後の対話と振る舞い / 戦闘状況 / 得られる情報 / エンディング。

単純な善悪二択、驚かせるためだけの予測不能な結果、それまでの全てを上書きする最終メニュー選択を避ける。

`docs/narrative-state.md` に、フラグ・前提条件・排他状態・クエスト遷移・キャラクター状態・帰結・エンディングを機械可読または明確な表形式で維持する。全経路を矛盾・到達不能コンテンツ・参照切れ・ソフトロックについて自動走査する。伏線と回収の台帳も維持する。

対話は声に出して自然に聞こえ、現在のゲーム状態を反映し、説明台詞を避け、各キャラクターの声を保つこと。重要情報は1つの文書や独白ではなく、行動・環境・会話・振る舞い・発見に分散させる。

## 7. ワールドとレベルデザイン

物語とゲームプレイの両方を支える、一貫した高密度の都市を1つ設計する。ジャンル的バイオームの寄せ集めとして設計しない。

体感的な広さは以下の組み合わせで作る: 垂直経路 / 視認できるランドマーク / 入れる屋内 / 屋上 / 地下や設備空間 / 近道 / 後に開放される封鎖路 / ステルス・戦闘・回避の代替ルート / 地理を教える見通し / 環境変化 / 新たな知識・能力・同行者・状況を得ての再訪。

環境は歴史を語ること。建築、放置された持ち物、損傷、応急修理、資源分布、標識、照明、音、NPC の振る舞いが、同一の出来事を裏付けること。ランダムな装飾にしない。

**場所は完了したミッションと決定に応じて可視的に変化すること。** ジャーナルのテキストだけで帰結を伝えない。

天候・時間帯・サバイバルメーター・クラフト・拠点開発・評判・スケジュール・乗り物・手続き的イベントは**任意**であり、必須項目ではない。採用する場合はコアループと物語に有意に絡み、他システムと同じ品質ゲートを通ること。

## 8. ゲームプレイとゲームフィール

完成品が最低限備えるもの: 応答性の高い三人称移動 / 衝突処理を持つ安定して読みやすいカメラ / 一貫したアクションまたは戦闘システム / 挙動が理解可能な脅威 / 意味のある発見を伴う探索 / 数値膨張ではなく戦略を変える RPG 進行 / サバイバルの調子に合った資源と報酬のペース / 失敗・復帰・セーブ・再開の導線 / プレイで教えるオープニング / 主要な葛藤を解決するエンディング。

**銃器・近接武器・ステルス・クラフト・レアリティ・スキルツリー・仲間・カバー・拠点建設をジャンル慣習だから追加しない。** 採用したシステムは、その存在を正当化する深さと、他要素との相互作用を持つこと。

戦闘と移動の優先事項: 即時の入力応答 / 読み取れる予備動作と硬直 / 一貫したヒット判定 / 有用なアニメーションキャンセル規則 / 明確なダメージと危険のフィードバック / 位置取りの判断 / 狭所での信頼できるカメラ / 公正な敵の知覚 / 説得力のある物理反応 / 強いが過剰でない視聴覚フィードバック / アクションを隠さないモバイル操作。

敵は挙動・知覚規則・強み・弱み・遭遇での役割で差別化する。HP とダメージの増加は多様性ではない。AI はナビゲーション失敗時に安全に復帰し、無効なジオメトリ越しに視認・射撃・攻撃しないこと。

進行は新しい判断・プレイスタイル・効率・経路・相互作用を生むこと。％を繰り返し増やすだけの強化を避ける。経済は直感ではなくシミュレーションと通しプレイでバランスを取る。

## 9. ビジュアルとテクニカルアート

**この節は本プロジェクト最大の制約を扱う。よく読むこと。**

フォトリアルなキャラクターモデルや手描きの高解像度テクスチャセットを制作することはできない。それを装ってはならない。同時に、無加工の Three.js プリミティブに逃げてもならない。ここでの「リアル志向」とは:

- **ジオメトリよりマテリアル。** 信じられる PBR 応答、一貫した摩耗、正しいスケール、統制されたパレット。これらはポリゴン数より効く
- **ライティング階層の設計。** 可能な限りベイク、リアルタイムライトは少数を意図的に配置、接地影と AO。**これが使える最大の武器である**
- **シルエットと構図。** 読み取れるランドマーク、明快な見通し、信じられるプロポーション
- **手続き的・モジュール的構築を前提とする。** モジュール建築キット、インスタンス化した瓦礫と小物、手続き的にバリエーションを持たせたファサード、テクスチャアトラス。よく作られた少数のモジュールを組み合わせる
- **第三者アセットの使用は許可され、想定されている。** 商用利用可のライセンスであり、出所・ライセンス・URL を `docs/assets.md` に記録すること。CC0 / パーミッシブを優先。著作権のあるゲーム・映画・ブランドの参照画像をトレース・複製・同梱しない
- アセットストアの寄せ集めに見えてはならない。スケール、マテリアル応答、摩耗、パレット、テクスチャ密度、UI の処理を全体で統一する

パイプライン: 最適化 glTF/GLB、KTX2/Basis 圧縮テクスチャ、Draco または meshopt、アトラス、インスタンシング、LOD、プール化エフェクト、チャンクストリーミング。**全てのエフェクトは性能テストを通過すること。通らないものは落とす。**

## 13. パフォーマンスと検証の誠実性

**最初のプレイ可能ビルドから iPhone SE 第3世代を基準に設計する。**

目標: 代表的な戦闘と移動で 30 FPS 以上を安定維持 / 条件が許せば 60 FPS / 長い停止のない一貫したフレームペーシング / エリア遷移を繰り返しても有界なメモリ / 起動時に全世界をロードせずチャンク化。

初期バジェット（証拠に基づき改訂可。改訂は必ず記録）:
- ドローコール 通常150以下 / 最悪250以下
- 可視三角形 通常30万以下
- テクスチャメモリ 200MB以下、最大辺2048
- 画面内スキンドメッシュ 8以下 / リアルタイム影キャスター 2以下
- 初期ペイロード 15MB以下 / 操作可能まで 4G で 8秒以下
- JS フレーム時間 8ms 以下

品質ティアと自動劣化を実装する: DPR 上限、動的レンダースケール、LOD、カリング、インスタンシング、影の制限、距離によるアニメーション間引き、AI 更新のずらし、エフェクト密度の低減。

### 検証の誠実性（必須）

**このプロジェクトの実行環境に iPhone SE は存在しない。** GitHub Actions のランナーもクラウドセッションも、物理端末を持たない。したがって:

- ゲーム内に性能 HUD とヘッドレス計測経路を実装する
- Playwright で CPU/GPU スロットリングをかけ、静穏な移動 / 高密度環境 / 戦闘 / エフェクト過多 / UI オーバーレイ / エリア遷移の各シナリオを計測する
- **全ての数値に、それを計測した正確な環境を併記する。エミュレーション結果はエミュレーションと明記する**
- **実機での結果を主張してはならない。示唆してもならない**
- `docs/device-test-checklist.md` を作成する。人間が実機で順に実行できる、合否基準付きの手順書とする

## 14. マルチエージェント体制

主統合者が製品ビジョン・アーキテクチャ・受け入れ表・統合・最終リリース判断を持つ。専門領域: 創作と物語 / ワールドとミッション設計 / 戦闘・進行・AI・物理・ゲームフィール / 環境アート・キャラクター・アニメーション・VFX・テクニカルアート / モバイル入力・UI・アクセシビリティ・オーディオ・ビルド・性能 / 自動 QA と通しプレイ検証。

**複数エージェントが同一ファイルを同時に編集しない。** ファイルまたはサブシステムの所有権を明示し、インターフェースを先に定義し、小さく検証しながら統合する。各サブエージェントは変更前に既存の作業を調査し、以下を報告する: 何を変えたか / なぜ / 何をテストしたか / 計測結果 / 残存リスク / 影響ファイル。

### 批評エージェントの独立性

**機能を作ったエージェントが、その機能を承認する唯一のエージェントであってはならない。** 独立した批評者を以下に置く: 物語と世界の整合性 / ゲームフィール・AI・バランス・遭遇の質 / ビジュアル・カメラ・アニメーション・VFX・UI・視聴覚表現 / モバイル操作性・性能・信頼性・コンテンツ完全性。

**批評エージェントは実装エージェントの報告や要約を入力として受け取ってはならない。** リポジトリ内の成果物、実際のビルド、`docs/DONE.md` の受け入れ基準のみを入力とすること。

## 15. 実装・批評・改善ループ

主要な決定・システム・エリア・ミッション群・キャラクターアーク・UI・性能マイルストーン・リリース候補は必ずこのループに入る:

1. 実装前に受け入れ基準とテストケースを明示する
2. 誠実にテストできる最小の完全版を実装する
3. 自動テスト・静的チェック・ビルド検証を実行する
4. 実際にゲームを動かし、該当箇所をプレイする
5. 証拠を取得する（スクリーンショット、フレーム計測、ログ、分岐結果、プレイ記録）
6. 独立した批評者が受け入れ基準に照らして評価する
7. 全指摘を severity・証拠・再現手順・対象箇所・推奨対応とともに記録する
8. 症状ではなく根本原因を修正する
9. 再ビルドし、回帰テストを含む全関連テストを再実行する
10. 終了基準を満たすまで繰り返す

**「良い」「問題なさそう」だけの批評は無効とし、ゲート通過の根拠にできない。** 批評は具体的な強み・弱み・証拠・残存リスクを挙げること。批評記録は `docs/reviews/` に残す。

同じ機能が繰り返し批評を通らない場合、基準を下げたり表面的な磨き込みを繰り返すのではなく、設計を変えるかスコープを縮小する。

外部作品をベンチマークにする場合、一般的な craft の次元のみを比較し、合法に入手した公開資料を使う。実施していない比較を実施したと主張しない。**テスト結果・ユーザー反応・端末計測・スクリーンショット・批評家の承認を捏造しない。**

## 16. プロダクションゲート

### Gate A — 創作基盤
複数方向を検討した / 選択案に明確な独自性がある / ゲームプレイ・物語・世界が相互に支え合う / バイブルが内的に一貫している / スコープがプラットフォームに対して信頼できる / スコープ確定数値が記載されている / 物語と設計の批評者に未解決の critical 指摘がない。

**Gate A を通過するまで、広範なコンテンツ生産を始めない。**

### Gate B — 代表的バーティカルスライス
コアループ・移動・カメラ・アクション・AI・探索・物語提示・UI・オーディオ・アートディレクション・セーブ・ロード・タッチ操作の最終品質の実例を1つ含む。

通過条件: 開発者の説明なしに楽しく理解できる / タッチ操作が基準画面サイズで機能する / ビジュアルが一貫している / 代表シーンで最低フレームレート目標を満たす / 批評ループが critical と high を全て解消 / アーキテクチャが脆いコードの複製なしに拡張できる。

**バーティカルスライスは品質ゲートであり、最終成果物ではない。**

### Gate C — コンテンツ完成
オープニングからエンディングまでプレイ可能 / バイブルのスコープ確定数値どおりに全エリア・遭遇・クエスト・物語ビート・UI 導線・音声キュー・進行段階が存在する / 全分岐と全エンディングに到達可能 / プレースホルダ・仮の台詞・機能しないボタン・TODO 画面・意図的な欠落が残っていない / セーブ・死亡・リトライ・リロード・復帰の導線が全編で機能する。

### Gate D — リリース候補
blocker と critical がゼロ / 通常プレイに影響する high がゼロ / クリーンセーブからの通し完走を実施済み / 分岐マトリクスで全対応経路を検証済み / 進行不能とソフトロックがない / 本番ビルドに未捕捉エラーとアセット欠落がない / 基準サイズと他のモバイルサイズでタッチレイアウトが通る / **性能目標を満たすか、実機検証が不可能な場合はその制約が計測結果と明確に区別されている** / ライセンスと帰属が完備 / 最終修正後に全批評者が再チェックを完了 / 受け入れ表に全主張の証拠がある。

## 17. テスト

## 18. 完了判定

`docs/DONE.md` を作成し、上記 Gate A〜D をそのまま完了条件として転記する。**新しい基準を発明しない。**

Gate D の各項目を「自動検証可能」と「そうでないもの」に分類し、自動検証可能なものには具体的な検証コマンドまたはスクリプトを紐付ける。

`docs/STATE.md` に `ALL_DONE` と記載してよいのは、以下を**全て**満たす時のみ:

1. 自動検証が全て通る（build / test / Playwright / 分岐走査 / プレースホルダ走査 / コンソールエラー走査 / ライセンス台帳）
2. `docs/reviews/` に Gate D の全項目について証拠付きの批評記録が存在し、未解決の critical / high がゼロ
3. 性能に関する記述が §13 の誠実性要件を満たしている（エミュレーション結果がそう明記され、実機主張がない）
4. `docs/device-test-checklist.md` が存在する

**この4条件を満たさないまま `ALL_DONE` を書くことは、§15 の捏造禁止に対する違反として扱う。**

## 19. セッション継続プロトコル

コンテキストは必ず尽きる。したがって:

- `docs/STATE.md` を進捗の唯一の情報源として維持する。常に次を含む: 現在フェーズ / 完了分 / **次の3アクション**（具体的な作業として） / ブロッカー / バイブル確定後の決定変更
- コンテキストが逼迫する**前に** STATE.md を更新してコミットする
- 小さく動く単位でコミットする。`main` は常に動作すること
- **記憶を持たない新しいエージェントが STATE.md だけを読んで再開できるように書く**
- 各フェーズは個別の PR とし、説明に変更内容・実行したテスト・計測結果・残存リスクを書く

## 20. 作業規則

- 編集前に既存リポジトリと現状を調査する。無関係な作業を保全する
- 計画・設計文書・モックアップ・メニュー・バーティカルスライスで止まらない
- 実装の欠落を、それがあればどうなるかという説明文で代替しない
- 未完成を「今後の拡張」で隠さない
- アセット・テスト・計測・スクリーンショット・比較・完了主張を捏造しない
- 開発を通じてゲームを常に実行可能に保つ
- 小さく統合し、小さく検証する
- 自己評価より証拠を優先する
- 全リリースゲートを通過するまで批評改善ループを継続する
