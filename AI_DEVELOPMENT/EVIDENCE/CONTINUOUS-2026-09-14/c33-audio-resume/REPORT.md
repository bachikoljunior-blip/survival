## Source-grounded cause and uncertainty

At fixed source `b0f1dfb9860dbc00018c0c587d8f0934fadb6604`, Audio._installUnlock (original lines 110–125) calls `_create`, sets `unlocked = true`, and removes all pointerdown/keydown/touchstart unlock listeners. `_create` sets `ready = true` and invokes asynchronous resume only if the context was initially suspended; it does not wait for a running state before those listeners disappear. The later Audio.update method does not resume the context. Existing visibility/focus handlers attempt resume, but there is no surviving gesture callback that requests resume of an already created suspended context.

The actual Safari harness refreshes/calibrates, taps Continue, performs its soak, and then calls captureIosAudio. The unchanged shared acquisition starts a new game programmatically and requests one normal native tap. The adapter only observes capabilities for up to five seconds; it intentionally does not call resume itself. If the existing context is suspended then, the normal tap cannot reach a removed Audio unlock listener. Engine execution and recording API availability can still be healthy while the audio context stays suspended.

Two conditional paths are reproduced with exact source methods: (1) creation succeeded, then the existing context later becomes suspended; (2) the initial resume request is rejected while ready/unlocked are already true. In both cases the original and `22add12...` versions have removed their gesture recovery path. The second is a deliberately injected CPU scenario, not a claim that the actual Safari log reported a rejection.

The original log has no per-request resume outcome or AudioContext statechange timeline. Its `observedTrustedTouch` is an `Array.some` over captured touch history, not an event-to-resume correlation for the final tap. Consequently, the initial suspension trigger, precise Safari interruption/policy behavior, and whether the final tap was the decisive missed recovery opportunity are hypotheses rather than measured causes. The definite code defect is the missing gesture recovery path, not a proven explanation of every Safari suspension. Input source reads show preventDefault rather than stopPropagation for the relevant canvas events; this candidate retains the existing listener phase.

## Minimal repair

Only `_installUnlock` changes. Its three existing input listeners remain installed for the Audio object's lifetime, reject events unless `event.isTrusted` is true, and create the graph only on the original first-unlock branch. On later genuine input, an existing context in exactly the suspended state receives `ctx.resume()` synchronously inside that handler. Running and closed contexts are left alone. The existing context is never replaced by this recovery branch. Initial graph creation, existing focus/visibility handling, gain/compressor construction, music/SFX, update behavior, and all recording/clock guards are unchanged.

There is no timer, capability retry loop, new AudioContext, injected browser gesture, synthetic unlock, recording substitution, or relaxed guard. A rejected resume or a closed context remains visibly not running and must still fail actual capture checks. Multiple real event types can each provide a recovery opportunity while suspended; there is no background polling or frame-driven resume.
